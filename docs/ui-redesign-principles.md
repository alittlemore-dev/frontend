# План улучшения UX/UI всей системы

Документ фиксирует подтверждённое направление: компактный интерфейс, который помогает
сосредоточиться на текущей задаче. Будущие экраны адаптируют эти принципы к своей задаче;
конкретные приёмы одного экрана не становятся обязательным шаблоном для всего сайта.

Расширенный аудит: 9 октября 2026 года. Общие принципы ниже сохраняют ранее принятое
направление. Разделы после них — предложения для будущей реализации, а не описание
уже выпущенных изменений. Цель: быстрее находить данные, выполнять частые действия,
понимать состояния и возвращаться к работе; компактность служит этим сценариям.

## Фокус и навигация

- В рабочем пространстве просмотра или редактирования глобальное дерево страниц не должно
  постоянно занимать полезную ширину, если оно не нужно для текущей задачи. Освободившееся
  пространство можно отдать содержимому или контекстной навигации.
- Путь назад должен быть понятен, а глобальная навигация — доступна. Сокращение визуального
  шума не должно затруднять переходы между разделами.
- На длинных экранах уместны информативные сворачиваемые группы и закреплённые ориентиры,
  если они помогают понимать положение и продолжать работу.

## Компактность и визуальная иерархия

- Элементы управления компактны и согласованы между собой; поля остаются читаемыми,
  а отступы помогают различать связанные и самостоятельные части формы.
- Основное действие сохранения хорошо заметно. Второстепенные и разрушительные действия
  визуально спокойнее, при этом их назначение и последствия понятны.
- Вложенные рамки, карточки и другие декоративные оболочки сокращаются там, где они
  не помогают структуре и пониманию содержимого.
- Новые экраны сохраняют преемственность с существующими темами и стилем приложения.
- Компоновка адаптируется к ширине экрана. Многострочные поля показывают вводимый текст
  без внутренней прокрутки.
- На широком экране самостоятельные группы полей и настроек можно размещать в колонках,
  чтобы сократить пустое пространство и вертикальную прокрутку. Поля сохраняют удобную
  ширину, связанные настройки остаются вместе, порядок чтения понятен. На узком экране
  группы располагаются последовательно; одна колонка уместна и на широком экране, если
  разделение ухудшает понимание содержимого.

## Сохранение функциональных контрактов

Редизайн сохраняет существующие возможности и поведение, доступность, валидацию,
видимое выделение некорректных полей, обратную связь по действиям и защиту несохранённых
изменений. Компактность не должна скрывать ошибки, важные состояния или необходимые
элементы управления.

## Границы принятых решений

Подтверждены принципы, а не универсальная схема экрана. Выбор контекстной навигации,
сворачивания и закрепления зависит от задачи и содержимого. Точные размеры и конкретная
компоновка определяются при работе над соответствующим экраном.

## Резюме как ориентир

Сильная сторона резюме — организация работы, а не количество небольших элементов.
На экране профиля видно три смысловые группы; в опыте сначала читаются компании
и краткие сводки, затем раскрываются детали. Основные действия и статус изменений
не конкурируют с глобальным деревом. Это позволяет быстро понять объект и перейти
к нужной части.

| Приём резюме                                    | Перенос в другие разделы                                             | Граница применения                                   |
| ----------------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------- |
| Шапка с именем объекта, состоянием и действиями | Деталки, формы, модерация                                            | В списке нужен заголовок коллекции и создание        |
| Контекстная навигация                           | Длинные редакторы, связи человека, аналитические разделы             | Короткую форму не дробить на вкладки ради сходства   |
| Свёрнутая группа со сводкой                     | Связи, параметры публикации, редактор события, служебные инструменты | Ошибки и критичные предупреждения остаются заметными |
| Отдельный preview                               | Статьи и вопросы, оформление документа                               | Не дублировать все режимы редактора на одной панели  |
| Колонки по смыслу                               | Контакты, параметры, бюджет                                          | Текст для чтения ограничивать по ширине              |
| Второстепенное меню действий                    | Списки и деталки                                                     | Частое основное действие остаётся сразу доступным    |
| Статус изменений и путь к ошибке                | Все редакторы                                                        | Реальный статус сервера, без имитации автосохранения |
| Keyboard reorder и undo                         | Упорядоченные группы и деревья                                       | Undo обещать только при наличии восстановления       |

У самого резюме остаются возможности для улучшения: навигация к конкретной ошибке
из общей сводки, более ясные подписи заполненности, менее заметные счётчики символов
далеко от лимита. Эти изменения не требуют переделки удачного каркаса.

## Общие решения для всей системы

### Три типа экрана

| Экран           | Основная компоновка                                                                 |
| --------------- | ----------------------------------------------------------------------------------- |
| Коллекция       | Заголовок и создание → поиск и активные фильтры → результаты → пагинация            |
| Объект/редактор | Назад и контекст → название и статус → содержимое и контекстные группы → сохранение |
| Обзор/аналитика | Период и контекст → несколько значимых итогов → детали и переходы к действиям       |

Публичное чтение использует ширину текста и спокойную типографику. Рабочие таблицы
используют доступную ширину. Компактный редактор не задаёт максимальную ширину
для статьи или плотность для календаря.

### Навигация и общий каркас

- На широком экране заменить техническое дерево разделов с +-- и линиями на
  компактные сгруппированные ссылки. Активный раздел выделять однозначно.
  Число дочерних пунктов убрать из визуальной навигации: оно не помогает пользователю.
- У workspace и админки сделать управление шириной навигации доступным и на desktop:
  раскрытая панель либо компактное меню разделов. Сохранить выбранное пользователем
  состояние как локальную UI-настройку с безопасным поведением при SSR.
- Оставить глобальное меню для перехода между сервисами, контекстное — для разделов
  текущего сервиса. При скрытой панели подписать кнопку «Разделы», чтобы назначение
  отличалось от глобального меню.
- Для account с тремя страницами достаточно компактных ссылок/вкладок; отдельная
  широкая колонка оправдана хуже, чем в большой админке.
- На мобильном убрать повторяющуюся крупную шапку «Рабочее пространство» над названием
  каждой коллекции. Название текущей страницы и доступ к разделам должны помещаться
  в один компактный блок.
- Возврат из объекта восстанавливает применённые фильтры, страницу и позицию списка.
  Прямая ссылка на объект получает осмысленный fallback к его коллекции.
  Переходы между связанными объектами сохраняют понятный путь.
- В шапке аккаунта на некоторых маршрутах виден технический alt-ключ
  siteBuild.hero.logoAlt. Проверить доступность перевода в нужном bundle и заменить
  его корректной локализованной подписью.

### Поиск и фильтры

- Базовая строка: поиск, частый фильтр, кнопка «Фильтры» с числом применённых
  ограничений. Сортировка остаётся рядом со списком; размер страницы — в пагинации.
- Дополнительные параметры раскрываются под строкой. На мобильном используют
  доступную выдвижную панель/секцию, сохраняя значения при закрытии.
- Применённые ограничения показывать краткими удаляемыми метками. Сбросить всё —
  доступное второстепенное действие. Закрытый блок не скрывает факт фильтрации.
- Поиск может применяться после короткой задержки с отменой предыдущего запроса,
  если текущий API это поддерживает. Для нескольких взаимозависимых параметров
  оставить явное «Применить»; не смешивать незаметно два способа применения.
- Различать вводимые и применённые значения. Enter запускает поиск, очистка
  предсказуемо сбрасывает запрос, смена ограничений возвращает на первую страницу.
- Пустая коллекция предлагает создать первую запись; нулевой результат поиска
  предлагает изменить или сбросить фильтры. Ошибка загрузки не выглядит как пустота.
- Существующие query-параметры сохранить. Новые фильтры добавлять только при реальной
  задаче и поддержке API; не фильтровать одну загруженную страницу как всю коллекцию.

### Строки, таблицы и действия

- Первым показывать название объекта; аватар/иконку объединять с названием.
  Второстепенные сведения помещать в спокойную вторую строку вместо отдельной
  колонки с повторяющимся «Не задано».
- На desktop оставлять таблицу там, где сравниваются числа или статусы. На мобильном
  представлять сущность строкой с названием, ключевыми метаданными и меню действий.
  Для финансов сохранить связь названий с числами; горизонтальная прокрутка допустима
  внутри действительно сравнительной таблицы, а не всей страницы.
- Название объекта делать настоящей ссылкой, сохраняя открытие в новой вкладке.
  Не делать строку единственной несемантической кликабельной областью.
- Частое действие показывать явно; редкие действия помещать в меню.
  Кнопка удаления не должна повторяться ярким акцентом в каждой строке.
- Длинное название переносится разумно, важная часть не исчезает. Для длинных наборов
  тегов/связей показывать краткую сводку и раскрытие полного списка.
- Пагинация сообщает диапазон и общее число, когда API возвращает totalCount.
  Единственную страницу показывать без двух бесполезных disabled-кнопок.
  На пустом результате не выводить «1 / 0».
- Общий вид списка не означает один универсальный компонент с бизнес-правилами
  всех доменов. Извлекать устойчивые примитивы после двух реальных применений.

### Формы, сообщения и визуальный язык

- Согласовать высоты контролов, отступы, радиусы, заголовки и способы обозначения
  активных режимов через существующие токены. Компактность не означает мелкий
  основной текст или недостаточную область нажатия.
- Основное действие создания/сохранения использует положительный акцент.
  Статус публикации, грейд и прочие признаки получают подписи; смысл не передаётся
  только цветом. Не выделять каждый признак отдельной яркой badge.
- Ввод, просмотр и preview различаются явно. Не превращать read-only данные в
  disabled-поля без необходимости. Короткие настройки не требуют отдельного режима.
- Для формы с ручным сохранением показывать «Есть изменения / Сохраняется /
  Сохранено / Не удалось сохранить». Для настроек с автосохранением сообщать статус
  каждого изменения и возможность повтора.
- При ошибке раскрыть нужную секцию, выбрать язык, прокрутить к полю и установить
  фокус. Сводка ошибок — набор переходов, а не дублирующий длинный текст.
- Краткий успешный результат показывать без накопления уведомлений; постоянная ошибка
  остаётся рядом с операцией. Соблюдать существующий лимит toast до 5 секунд.
- Textarea увеличивается по содержимому. Для больших Markdown-редакторов сохранить
  контролируемую высоту и fullscreen, чтобы длинный документ не поглощал весь экран.
- Простое создание — короткий dialog; длительное создание статьи/вопроса — полноценный
  редактор. Перенос создания на маршрут делать отдельной задачей, сохраняя guards,
  отмену и возврат в список; не предлагать неподдерживаемое сохранение пустого черновика.
- Закреплённые панели не перекрывают ошибки, последнюю строку, popover и экранную
  клавиатуру. Желателен один основной scroll-контейнер.

### Резюме: коллекция — /personal-workspace/resumes · P1

- Оставить название, язык, профиль/роль и обновление; дату создания убрать из

- Поиск/языковой фильтр добавлять при поддержке API; локальная фильтрация текущей

**Приёмка:** семь существующих документов различимы на 390 px; название, язык,
роль и время обновления видны без горизонтальной прокрутки.

### Редактор резюме — /personal-workspace/resumes/:id · P2

- Сохранить нынешнюю композицию как ориентир. Доработать переход из сводки ошибок

**Приёмка:** длинное резюме можно исправить, проверить и экспортировать,

**Приёмка:** разовое, еженедельное и многодневное событие понятны без открытия;

### Финансовый обзор — /personal-workspace/finance · P1

- Согласовать размер заголовка; период и навигацию собрать в одну компактную шапку.

- Для операций: добавить ясную общую точку входа «Добавить операцию» с выбором
  расхода/дохода; история и удалённые записи раскрываются по запросу.
- На мобильном переключать доходы/расходы или складывать их последовательными группами,
  сохраняя название, сумму и валюту вместе. Не прятать смысл в пустых колонках.
- Архивацию категории и окончательное удаление различать по последствиям.
  Сохранить существующие ограничения и возможность восстановления операций.

**Приёмка:** категория с длинным именем и все денежные значения читаются;
пользователь понимает, сохранилась ли inline-правка; прошлый месяц не выглядит
полностью редактируемым.

### Финансовая статистика — /personal-workspace/finance/statistics · P1

- Первая строка — период, валюта и фактический диапазон. Сводка — доходы, расходы,
  разница и сравнение с предыдущим периодом.
- Заменить крупные отдельные диаграммы единственного начального/конечного остатка
  компактными числами или одним осмысленным сравнением.
- Динамика и категории получают основное пространство. Повтор бюджета текущего месяца
  свернуть в дополнительную группу или дать ссылку на обзор.
- План и факт показывать совместно там, где сравнение осмысленно; длинные категории
  не превращать в обрезанную легенду. Сохранить доступную табличную альтернативу.
- Объяснить неполное покрытие и сравнение с полным предыдущим периодом рядом с итогом.
  При нескольких валютах не складывать их без существующего контракта конвертации.

**Приёмка:** смысл изменения виден до прокрутки; графики отвечают на вопрос
о динамике/структуре, а показатели покрытия и валюты понятны.

## Админ-панель: план по страницам

**Приёмка:** смысл выдаваемого доступа понятен; существующие show/copy/revoke

### 404 — /404 и неизвестный маршрут · P3

- Объяснить, что страница не найдена, и дать переход к публичной главной,
  статьям/матрице либо доступному рабочему разделу.
- Сохранить корректный SSR/status-контракт; публичные и защищённые неизвестные
  маршруты не раскрывают приватные данные.

**Приёмка:** несуществующий URL имеет понятный следующий шаг и корректное
поведение сервера/роутера.

### Шапка, footer и уведомление о хранении данных · P2

- Согласовать активный сервис, доступ к разделам и аккаунту; icon-only элементы
  имеют локализованные доступные имена.
- Footer оставить компактным, длинные ссылки адаптировать на мобильном.
  Он не создаёт излишнюю пустоту под короткими рабочими страницами.
- Уведомление о локальном хранении данных сделать читаемым и компактным;
  оно не перекрывает основное действие/последнюю строку.
  Не менять существующую политику хранения ради визуальной компактности.

**Приёмка:** меню и уведомления работают с клавиатуры, на узком экране и при
длинных переводах; текущий сервис узнаваем.

## Быстродействие и сложность реализации

Сокращать отдельно время выполнения задачи, объём загрузки и сложность кода.
Меньшее число рамок не доказывает ускорение приложения. Перед оптимизацией снять
baseline на одинаковых данных и условиях; ниже — кандидаты, а не найденные регрессии.

| Кандидат                | Основание в текущем коде/экране                                                          | Следующее действие                                                                                                   |
| ----------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Календарная зависимость | Calendar component импортирован в dashboard статически, хотя создаётся только на вкладке | Проанализировать chunk; рассмотреть динамическую загрузку календаря после открытия                                   |
| Скрытые панели          | В нескольких экранах используются hidden и большие редакторы                             | Измерить число активных редакторов/DOM; отложить инициализацию тяжёлых панелей, сохраняя форму и черновики           |
| Фото людей              | Отдельная загрузка файла для каждого фото страницы                                       | Ограничить параллелизм и загружать нужные фото; не публиковать private object URL                                    |
| Повторный поиск         | Некоторые поисковые/связанные запросы запускаются из ввода                               | Проверить debounce, distinct и отмену/игнорирование устаревших ответов                                               |
| Обновление списка       | Loading-ветки могут заменять данные spinner                                              | Сохранить предыдущие строки с локальным pending при повторном запросе; новая выборка не притворяется уже загруженной |
| Сводки дашбордов        | Независимые API и ролевые варианты                                                       | Загружать нужный контекст, не ждать все блоки для показа одного                                                      |
| Финансовые графики      | Большие повторяющиеся визуализации                                                       | Уменьшить бессмысленные графики и объём DOM, затем измерить рендер                                                   |
| Длинные коллекции       | Серверная пагинация уже есть у ряда списков                                              | Сначала использовать её и стабильный track; virtualization вводить только после подтверждения проблемы               |
| CSS и shared chunks     | Bootstrap, SCSS и design system сосуществуют                                             | По отчёту сборки найти дубли/неиспользуемые зависимости; не менять тему целиком без причины                          |
| Public SSR              | Уже существуют SSR smoke и Lighthouse с fixture server                                   | Сохранить transfer-cache/SEO/CSP-контракты, сравнивать supported checks до/после                                     |

Не кешировать приватные списки в общем SSR/transfer-cache. Локальная память
клиента может сохранять безопасное UI-состояние; изменение данных инвалидирует
соответствующие результаты. Не добавлять store-библиотеку, новый набор контролов,
новый E2E-фреймворк или монолитный «универсальный workspace» в качестве условия редизайна.

Рабочий baseline для каждого выбранного пилота:

1. Холодное открытие и повторный переход: число запросов, размер загруженного JS/CSS,
   время до появления пригодных для работы данных.
2. Поиск/смена фильтра: запросы, устаревшие результаты, мерцание и сохранение фокуса.
3. Раскрытие редактора/календаря: задержка реакции и число созданных тяжёлых компонентов.
4. Длинный список/форма: прокрутка, переносы, рост DOM и сохранение позиции.
5. Полный сценарий: действия, ошибки и время до результата на desktop/mobile.

Для public-страниц использовать существующий make lighthouse. Конфигурация
lighthouserc.cjs уже задаёт median performance ≥ 0.9, LCP ≤ 2500 ms,
TBT ≤ 200 ms и CLS ≤ 0.1 на своём стенде. Это текущие пороги проекта,
не результаты этого аудита и не измерения защищённых маршрутов.
Для protected CSR-страниц нужны отдельные browser traces с тестовым входом;
публичный Lighthouse их не покрывает.

### Владельцы и границы

- Основной UI и routing — frontend. Бизнес-данные/новые query-возможности:
  competency-trainer для статей/матрицы, personal-workspace для личных данных/финансов.
- Общие визуальные примитивы и токены — design-system, после подтверждения
  повторного использования; выпуск пакета имеет свой workflow.
- Новые UI-подписи и языки — i18n; авторский контент статей/матрицы локализуется
  через их существующие API.
- Профиль и предпочтения — auth-api; приглашения и связи Telegram остаются
  в сервисе bot. Infra отвечает за стенд и runtime.
- Визуальные задачи обычно не требуют backend. Новый фильтр, summary или create-flow
  сначала трассируется через существующее хранение, API и клиент; новый endpoint
  появляется только с отдельной ответственностью.

## Приёмка изменений

Каждая задача завершает пользовательский сценарий, а не только заменяет стили.

| Проверка     | Репрезентативный сценарий                                                                                   |
| ------------ | ----------------------------------------------------------------------------------------------------------- |
| Коллекции    | Нет записей; нет совпадений; ошибка; loading; 1 запись; 20+ записей; длинные названия/теги; две страницы    |
| Возврат      | Фильтр → page 2 → деталка → назад; прямой URL; browser back/forward                                         |
| Формы        | Заполненная/неполная форма; ошибка в свёрнутом блоке и EN; ручной revert; ошибка сервера; уход с правками   |
| Календарь    | Разовое/повторяющееся/весь день; плотный день; смена периода; часовой пояс; возврат из editor               |
| Финансы      | Длинная категория; пустой план; превышение; другая валюта; прошлый месяц; late operation; ошибка inline     |
| Admin        | Owner/admin/moderator; недоступное действие; публикация/черновик; queue import с дублями                    |
| Адаптивность | 390 px, промежуточная ширина, 1440 px; масштаб текста; экранная клавиатура; длинный RU/EN                   |
| Доступность  | Tab/Shift+Tab, Enter/Escape, focus return, именованные иконки, state announcements, reorder без мыши        |
| Темы         | Светлая/тёмная/системная по существующим возможностям; контраст текста, focus и ошибок                      |
| Public       | SSR, канонические языковые ссылки, wiki, метаданные, отсутствующий объект, отсутствие private transfer data |

Для реализации применять соответствующие проектные команды make test, make lint,
make typecheck, make format-check и make build по риску изменения; для SSR/SEO —
также make ssr-smoke, для затронутой public-производительности — make lighthouse.
Проверять изменённые API-контракты в каждом затронутом backend/i18n/design-system.
В этом аудите код приложения не изменяется, а данные локального стенда проверены
по количеству записей и отображению наполненных страниц.

Не добавлять тесты на точную вложенность HTML, названия CSS-классов и редакционный
текст ради редизайна. Регрессии проверять по поведению: фильтр, сохранение,
валидация, guard, фокус, роль, query и API. Screenshot фиксирует компоновку,
но не заменяет проверку контракта.
